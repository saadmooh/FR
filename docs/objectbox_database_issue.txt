OBJECTBOX DATABASE ISSUE - WorkManager Problems
==============================================

The database that WorkManager is having problems with is: OBJECTBOX

What is ObjectBox?
------------------
ObjectBox is a local NoSQL database (objectbox.g.dart) used for persistence
in the Flex Reminder app. It stores all Reminder entities, FreeTimeSlot
entities, RescheduleLock entities, and CategoryStatistic entities.

Why WorkManager Has Problems With It
-------------------------------------
ObjectBox does NOT allow two processes (isolates) to open the same store
file simultaneously. This creates a fundamental conflict:

  - Main isolate (foreground app) keeps the store OPEN during normal use
  - WorkManager runs in a BACKGROUND isolate and needs its own Store instance
  - Both try to access the same underlying database file

The Current Workaround (Fragile)
--------------------------------
The app tries to manage this with a close/reopen dance:

  1. App goes to background -> _closeMainStoreForBackground() closes the store
  2. WorkManager starts -> _openStoreInBackground() opens the store
  3. App returns to foreground -> _reopenMainStoreIfNeeded() reopens the store

StoreBusyGuard
--------------
A static guard (StoreBusyGuard) tracks active write operations to prevent
closing the store mid-transaction:

  - beginWrite() increments _activeWrites
  - endWrite() decrements _activeWrites
  - isBusy returns true if _activeWrites > 0
  - If busy, _closeMainStoreForBackground() defers (waits up to 2.5s via retries)

The Problem Flow
----------------
  App in foreground -> Store is OPEN in main isolate
       |
       v
  Notification triggers WorkManager
       |
       v
  WorkManager tries to openStore() -> FAILS: "another store is still open"
       |
       v
  Waits 30 seconds, retries up to 5 times (2.5 minutes max)
       |
       v
  If main isolate finally closes -> SUCCESS: opens
  If timeout -> FAILS: throws exception, task fails, no reschedule happens

Specific Error Cases
--------------------
  1. "another store is still open" - Main isolate hasn't released the store yet
  2. StoreBusyGuard.isBusy == true - A write is in progress, close is deferred
  3. Store reopen fails on foreground resume - App can't access DB after background
  4. Race condition - Main isolate closes AFTER WorkManager has already failed

The store directory path is passed from NotificationService to WorkManager
via WorkManager inputData ('storeDirectory' key) so both use the same file.

Impact
-------
When this database locking issue occurs:
  - WorkManager task fails entirely
  - No reschedule happens
  - Lock is never released (DEADLOCK)
  - No monitoring task registered for the rescheduled reminder
  - User gets no SnackBar notification of the reschedule
  - Subsequent WorkManager retries also fail until the store is fully released
