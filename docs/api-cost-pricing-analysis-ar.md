## 1. بيانات الموديل والاستخدام

| البند | القيمة | المصدر |
|---|---|---|
| الموديل المستخدم فعليًا | **`gemini-3.1-flash-lite`** | إعداد السيرفر الافتراضي في `supabase/functions/ai-proxy/index.ts:82` وجدول `ai_proxy_config` في `supabase/migrations/202608110002_config.sql:32` |
| نقطة الاستدعاء | Google Generative Language API عبر Edge Function وسيطة (`ai-proxy`) | `ai-proxy/index.ts:243-256` |
| Input price | **$0.10 / مليون توكن** (فئة Flash-Lite) | تسعيرة Google المعلنة للفئة |
| Output price | **$0.40 / مليون توكن** (فئة Flash-Lite) | تسعيرة Google المعلنة |
| Prompt caching | **غير مستخدم** — الطلب عبارة عن `generateContent` عادي بدون `cachedContent`، والـ system prompt يُرسل نصيًا داخل البرومبت من العميل | `ai-proxy/index.ts:236-256`, `lib/services/ai_service.dart:66-82` |

ملاحظات مهمة من الكود:
- الموديل **قابل للتغيير من Supabase Dashboard بدون تحديث التطبيق** (`gemini_model` في `ai_proxy_config`)، أي يمكن التحكم بالتكلفة ديناميكيًا.
- قيم الموديلات في `lib/core/constants.dart:8-46` (gemini/gpt/claude...) هي **قوائم عرض فقط** — الطلب الفعلي يمر حصريًا عبر البروكسي الذي يستخدم `geminiModel` من الإعدادات.
- حد أقصى للبرومبت: **4000 حرف (~1000 توكن)** يرفضه البروكسي (`ai-proxy/index.ts:361-369`).
- `maxOutputTokens` من السيرفر: **2048** (`ai-proxy/index.ts:252`). باراميتر `maxTokens` في `AIService._callAI` لا يُرسل للسيرفر (رمز غير فعّال حاليًا).
- لو تم تفعيل context caching لاحقًا (system prompts متكررة جدًا)، نسبة التوفير المتوقعة على الـ input: **~75-90%** على الجزء المخزّن (تسعيرة cached input لجوجل)، لكن مع أحجام البرومبت الحالية الصغيرة القيم موفَّرة تُقاس بالسنتات فقط — الأولوية ليست هنا.

## 2. حجم الطلب الواحد (per request)

التقديرات أدناه مشتقة من نصوص البرومبت الفعلية في `lib/services/ai_service.dart` (بقياس ~4 أحرف/توكن):

| النقطة | System prompt | بيانات مرفقة (سياق) | Output المتوقع |
|---|---|---|---|
| `classifyContent` (عند الحفظ) | ~15 توكن | ~120-250 توكن (title/description + قائمة التصنيفات) | 120-200 توكن (JSON بثلاث لغات) |
| `estimateBestTime` (عند الحفظ) | ~20 توكن | ~100-450 توكن (free times + reminders مجدولة) | 60-100 توكن |
| `fetchMetadata` (fallback نادر فقط عند فشل scraping) | ~20 توكن | URL فقط ~20 توكن | 100-200 توكن |
| `reschedulePostRaw` (WorkManager خلفي) | ~20 توكن | ~100-350 توكن (سجل المحاولات + free times) | 60-120 توكن |
| `reschedulePost` (يدوي من UI) | ~20 توكن | نفس الأعلى | 60-120 توكن |
| `analyzeStats` / `analyzeCategoryStatistics` (شاشة الإحصائيات) | ~15-20 توكن | ~150-400 توكن | 60-400 توكن |

**المعدلات المرجّحة** (الاستخدام المهيمن هو حفظ بوست = تصنيف + وقت أفضل):

- **متوسط Input لكل طلب: ~300 توكن**
- **متوسط Output لكل طلب: ~130 توكن**

**إعادة الإرسال (retries):**
- العميل يعيد المحاولة **مرة واحدة فقط** عند أخطاء شبكة (`SocketException`/`TimeoutException`) — `lib/services/ai_proxy_service.dart:94-185`.
- فشل Play Integrity قبل الوصول للبروكسي لا يكلف شيئًا.
- خطر مزدوج الفوترة موجود نظريًا عند Timeout بعد تنفيذ Gemini على السيرفر، عمليًا **~3-5%** زيادة متوقعة.
- فشل استدعاء Gemini نفسه (502) لا يُعاد تلقائيًا من العميل.

## 3. تكرار الاستخدام لكل مستخدم

### مصادر الاستدعاء (من الكود)
1. **حفظ بوست** (`save_post_sheet.dart:149-185`): 2 استدعاء عادة (تصنيف + وقت أفضل)، 3 إذا فشل الـ metadata fetching العادي.
2. **إعادة جدولة تلقائية** (`workmanager_service.dart`): تُطلق عند مرور وقت التذكير دون فتح، ثم تعيد جدولة نفسها حتى بلوغ السقف حسب الأهمية (`_getMaxReschedules`):
   - Day: 1 استدعاء كحد أقصى لكل تذكير
   - Week: 2
   - Month: 3
3. **إعادة جدولة يدوية** من شاشة التذكيرات/تفاصيل البوست (تفاعل مستخدم).
4. **تحليل الإحصائيات**: تفاعلي عند الطلب فقط.

### الجواب عن الأسئلة
- **استدعاءات/يوم لمستخدم نشط:** خفيف (1-3 حفظ/يوم) ≈ **3-6/يوم** · ثقيل ≈ 15-30/يوم.
- **آلية الاستدعاء:** مزيج — الحفظ والإحصائيات تفاعلية؛ إعادة الجدولة تلقائية (WorkManager) لكنها **محدودة بسلسلة محدودة لكل تذكير** وليست دورية ثابتة (لا يوجد `registerPeriodicTask` في الكود).
- **الحد الأقصى شهريًا (worst case):** **500 استدعاء/شهر** — سقف صارم على السيرفر `rate_limit_per_month = 500` (`config.sql:31`، مطبق في `check_rate_limit`)، مع سقف إضافي **1 طلب/ساعة** و 10/دقيقة.
- **توزيع الثقل (افتراض تشغيلي، ليس في الكود):** ~85% خفيف (~120 استدعاء/شهر) و ~15% ثقيل (~400 استدعاء/شهر) → **المعدل المرجّح ≈ 160 استدعاء/مستخدم/شهر**.

> **نقطة جوهرية من الكود:** كل استدعاءات AI تتطلب اشتراك Pro فعّال — البروكسي يرفض بدون session JWT صادر من `session-token` والذي لا يُصدر إلا بعد تأكيد entitlement من RevenueCat (`session-token/index.ts:1-13`, `ai-proxy/index.ts:515-543`). أي أن **المجانيين لا يستهلكون من ميزانية الـ API تقريبًا** — التكلفة تدفعها الإيرادات مباشرة.

## الحسابات المطلوبة

### المعطيات الرقمية

```
متوسط input/request  = 300 توكن
متوسط output/request = 130 توكن
سعر input            = $0.10 / مليون
سعر output           = $0.40 / مليون
استدعاءات/مشترك/شهر  = 160 (مرجّح) · 500 (سقف worst case)
```

### (1) تكلفة API لكل مشترك/شهر

```
تكلفة الطلب الواحد = (300 × 0.10 + 130 × 0.40) / 1,000,000
                   = (30 + 52) / 1,000,000 = $0.000082

شهريًا (مرجّح):  160 × $0.000082 ≈ $0.013
worst case (500): 500 × $0.000082 ≈ $0.041
```

| السيناريو | توكنات input شهرية | توكنات output شهرية | التكلفة/مشترك |
|---|---|---|---|
| خفيف (120 طلب) | 36K | 15.6K | **$0.010** |
| مرجّح (160 طلب) | 48K | 20.8K | **$0.013** |
| ثقيل (400 طلب) | 120K | 52K | **$0.033** |
| السقف (500 طلب) | 150K | 65K | **$0.041** |

> حتى لو ضُربت التقديرات ×2 (توكنات أعلى من المتوقع) تبقى التكلفة <$0.10/مشترك. **موديل flash-lite يجعل API غير عامل التكلفة الحاسم إطلاقًا.**

### (2) التكلفة الإجمالية لكل مشترك (مع البنية والعمولة)

سيناريو أساسي: MAU = 1,000 · تحويل 5% → **50 مشتركًا**

```
تكاليف شهرية:
  API (50 مشترك × $0.013)      = $0.65   (worst case: $2.05)
  Supabase Pro                 = $25.00
  RevenueCat/misc              = $0
  ──────────────────────────────────────
  الإجمالي                     ≈ $26     (~$27.05 worst case)

تكلفة حقيقية/مشترك قبل العمولة = $26 / 50 ≈ $0.52
```

| سعر الاشتراك | صافي بعد 15% Play | صافي بعد 30% Play |
|---|---|---|
| $1.99 | $1.69 | $1.39 |
| $2.99 | $2.54 | $2.09 |
| $3.99 | $3.39 | $2.79 |

### (3) السعر المقترح (هامش ×3 و ×5)

على التكلفة المحمَّلة الكاملة لكل مشترك ($0.52):

| الهامش | السعر الناتج | سعر مقترح تسويقيًا | الهامش الفعلي بعد كل شيء* |
|---|---|---|---|
| ×3 | $1.56 | **$1.99** | ~70% |
| ×5 | $2.60 | **$2.99** | ~76% |

\*(السعر − عمولة 15% − تكلفة متغيرة/مشترك) ÷ السعر

**التوصية: $2.99/شهر** — يغطي هامش >×5، ويظل تحت الحاجز النفسي $3، مع ترك مساحة لخطة سنوية ($24/سنة ≈ خصم 33%).

### (4) نقطة التعادل (Break-even)

```
التكاليف الثابتة الشهرية = $25 Supabase (+ $2 احتياطي) ≈ $27

B/E = التكاليف الثابتة ÷ الصافي الشهري للمشترك
```

| السعر | صافي (بعد 15%) | عدد المشتركين للتعادل | كنسبة تحويل عند MAU 1,000 |
|---|---|---|---|
| $1.99 | $1.69 | **16 مشتركًا** | 1.6% |
| $2.99 | $2.54 | **11 مشتركًا** | 1.1% |
| $3.99 | $3.39 | **8 مشتركين** | 0.8% |

(سيناريو متحفظ بعمولة 30%: التعادل عند $2.99 يتطلب **13 مشتركًا**.)

## الخلاصة التنفيذية

1. **تكلفة الـ API شبه معدومة** (~1.3 سنت/مشترك/شهر) بفضل `gemini-flash-lite` والسقوف الصارمة (500/شهر + 1/ساعة) وبأن الميزات الذكية مقفلة للمشتركين فقط.
2. **العنصر المهيمن على التكلفة هو Supabase الثابت ($25)** وليس التوكنز — القرار الصحيح هو التركيز على conversion rate وليس خفض استهلاك الـ API.
3. **سعر مقترح: $2.99/شهر** (هامش ×5+) — نقطة التعادل ~11 مشتركًا فقط.
4. **بنود ناقصة يجب إضافتها للكود قبل التوسع:** تتبّع MAU واستهلاك فعلي لكل مستخدم (جدول `usage` في Supabase)، وتفعيل prompt caching عند تجاوز 10K مشترك، ومراقبة `ai_proxy_config` لتخفيض الموديل عند الحاجة.
